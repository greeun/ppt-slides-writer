# 정보설계 원칙 (스토리라인·장표 구조)

발표자료의 설득력은 장표 수가 아니라 **장표별 역할과 논리 관통 구조**에서 나온다.
아래 원칙은 확정 규칙이며, Planner의 spec.md·Generator의 storyline.md·Evaluator의
채점(루브릭 C1) 전부가 이 문서를 기준으로 삼는다.

## 1. 단일 원천 (Single Source of Truth)

- **스토리라인 설계서(storyline.md)가 진실이다.** HTML/PPTX/PDF는 투영이다.
- 설계서에 없는 콘텐츠(주장·수치·사례)가 장표에 등장하면 위반이다
  (Evaluator 프로브 9가 역방향 대조로 검출).
- 수정도 같은 방향이다: 콘텐츠 변경은 storyline.md를 먼저 고치고 장표에 반영한다
  (workflows/05-revision.md).

## 2. 슬라이드 수보다 장표별 역할

- 모든 장표는 **역할(data-role) 1개와 키 메시지 1개**를 가진다.
- 역할이 설명되지 않는 장표("있으면 좋은 정보")는 삭제 후보다.
- 역할 enum과 의미:

| data-role | 설득 기능 |
|---|---|
| cover | 첫인상 — 제목이 곧 핵심 주장 |
| agenda | 여정 예고 — 청중이 따라올 지도 |
| section-divider | 호흡 전환 + bridge 수행 |
| problem | 긴장 조성 — 손실·리스크를 수치로 |
| insight | 관점 전환 — 데이터에서 뽑은 비자명한 발견 |
| solution | 해소 — problem의 수치를 직접 받아서 푼다 |
| concept | 원리 설명 — 왜 그 해법이 작동하는지 핵심 개념 1개 |
| process | 방법론 — 순서가 있는 단계별 실행 절차 |
| evidence | 신뢰 — 출처 있는 수치·사례·데모 |
| comparison | 판단 — 기준 열이 있는 비교 |
| case | 실증 — before/after가 있는 사례 |
| tactics | 실행 지침 — 청중이 내일 바로 적용할 요령·체크리스트 |
| caveats | 한계·유의사항 — 적용되지 않는 조건을 먼저 밝혀 신뢰를 얻는다 |
| application | 확장 적용 — 다른 맥락·2차 사용처로의 전이 |
| roadmap | 실행 가능성 — 시점·마일스톤 |
| team | 수행 주체 신뢰 |
| financials | 수치 신뢰 — 가정이 명시된 재무 |
| cta | 행동 — 구체적 다음 액션. URL은 `<a href>`로 감싼다(PPTX·PDF에서 클릭 + 클릭 추적 UTM 부여 가능 — workflows/07) |
| appendix | 질문 대비 — 발표 본선 밖 |

## 2-1. 기본 10장 골격 (구조 미지정 시 출발점)

사용자가 구조를 지정하지 않았고 발표 시간이 10~15분이면 아래 역할 배열에서 출발한다.
**고정 템플릿이 아니라 출발점**이다 — spec.md의 청중·목적에 따라 역할을 빼거나 더한다
(§2의 원칙이 우선: 역할이 설명되지 않는 장표는 삭제 후보).

| # | 역할 | 그 장표가 해내야 할 일 |
|---|---|---|
| 1 | cover | 제목이 곧 핵심 주장 + 부제 + 발표자 |
| 2 | problem | 청중이 겪는 문제를 수치로 |
| 3 | solution | 이 접근이 상황을 어떻게 바꾸는가 |
| 4 | concept | 그 변화를 만드는 핵심 원리 1개 |
| 5 | process | 단계별 실행 절차 |
| 6 | case | 사례·유스케이스 실증 |
| 7 | tactics | 적용 요령 — 청중이 내일 할 수 있는 것 |
| 8 | caveats | 한계·유의사항 |
| 9 | application | 2차 활용처로의 확장 |
| 10 | cta | 구체적 다음 행동(데모·다운로드·미팅) |

- **caveats 장표를 기본 포함한다.** 한계를 먼저 밝힌 덱이 질의응답에서 무너지지 않는다.
  10장 이상 덱에서 caveats가 없으면 Evaluator가 C1 감점 근거로 삼는다.
- 시간이 5분 이하면 concept·application·tactics 순으로 접고, 20분 이상이면
  evidence·comparison·roadmap을 사이에 넣어 확장한다.
- 이 골격을 그대로 쓰든 변형하든 §3 spine·§5 bridge 요구는 동일하게 적용된다.

## 3. 시나리오 spine (수치·주장 관통 구조)

- 앞 장표의 수치·주장이 **뒤 장표의 근거로 재등장**해야 한다.
  예: problem의 "연 3.2억 손실" → solution의 절감 근거 → cta의 ROI 계산.
- storyline.md의 "시나리오 spine" 표에 첫 등장/재등장 지점을 명시한다.
- spine이 없는 덱은 장표를 섞어도 이야기가 무너지지 않는다 — 그것이 나열의 증거다.

## 4. micro-flow (장표 내부 전개)

장표 내부는 **상황 → 문제 → 기준 → 예제 → 연결** 순으로 전개한다.
불릿 3~5개가 이 순서를 따르면 한 장 안에서도 논증이 성립한다.
같은 층위의 명사구만 나열된 불릿은 micro-flow 위반이다.

## 5. bridge 3문장 (섹션 전환부)

섹션이 바뀌는 장표(section-divider 또는 섹션 첫 장)의 발표자 노트에:
1. **이전 요약 1문장** — 방금까지 확인한 것
2. **전환 근거 1문장** — 왜 지금 이 주제로 넘어가는가
3. **다음 예고 1문장** — 이제 무엇을 볼 것인가

형식적 bridge("다음은 시장 규모입니다")는 1문장짜리 목차 읽기다 — 3문장 구조를 지킨다.

## 6. 제목·부제·본문 역할 분리

- **제목 = 주장** ("오분류 비용은 연 3.2억 원입니다" — o / "비용 분석" — x)
- **부제 = 키 메시지** (data-key-message와 일치)
- **본문 = 근거** (출처 있는 수치, 구체 사례)
- 제네릭 제목("핵심 기능", "Our Solution", "왜 우리인가")은 lint 체크 13이 WARN 처리.

## 7. 표 셀 판단 근거

표의 각 셀 값은 나열이 아니라 **판단(비교 기준)** 을 드러내야 한다.
- 기준 열이 있는가? (무엇으로 비교하는지)
- 각 셀이 그 기준에 대한 답인가?
- 스펙 나열표("기능 A: 있음")는 판단표("도입 후 오분류율: 3.7%→0.4%")로 바꾼다.

## 8. 발표 시간 정합 (±10%)

- 장별 예상 시간 합 = 발표 시간 **±10%** (lint 체크 16 — WARN).
- 산정 기준: **1분당 1~1.5장**. 10분 발표 = 10~15장.
- cover·section-divider는 0.5분 이하, 핵심 evidence·solution은 1.5~2분 배분이 자연스럽다.
- 시간이 넘치면 장표를 빼는 것이 먼저다 — 말 속도를 올리는 계획은 실패한다.

## 9. 청중 감정 곡선

도입 **긴장**(problem) → 중반 **신뢰**(evidence·case) → 종반 **행동**(cta).
곡선이 평평한 덱(전부 evidence)이나 역행하는 덱(cta 뒤에 problem)은 구조 재설계 대상.
리드마그넷형은 곡선 끝에 다운로드·후속 접점 동선을 추가한다.
